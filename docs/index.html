Modelo de datos

1 notificación = 1 registro en BD. El sistema es 1:N puro. El filtro se aplica en lectura, no en creación.

Tabla: notifications
┌──────────────────────────────────────────────────────────────┐
│ id            │ UUID (PK)                                              │
│ tenant_id     │ FK → tenants                                        │
│ app_id        │ "baco", "nexo", "crm"                                  │
│ title         │ "Ticket SUP-001 asignado"                            │
│ message       │ "Asignado al equipo Soporte"                            │
│ type          │ info │ success │ warning │ error                       │
│ priority      │ low │ normal │ high │ urgent                        │
│ target_user_id │ null = broadcast / string = personal           │
│ metadata      │ JSONB (GIN index) — app-specific                     │
│                │ ej: { "teamId": "soporte" }                        │
│ expires_at     │ created_at + 7 días                                 │
│ deleted_at     │ soft delete (null = activa)                            │
│ created_at     │ now()                                                │
└──────────────────────────────────────────────────────────────┘
Tabla: notification_reads
┌──────────────────────────────────────────────────────────┐
│ notification_id │ FK → notifications (CASCADE)                    │
│ user_id         │ UUID                                           │
│ read_at         │ now()                                           │
│ UNIQUE(notification_id, user_id)                          │
└──────────────────────────────────────────────────────────┘

1 broadcast = 1 fila en notifications. Cada usuario que la lee = 1 fila en notification_reads. Sin duplicación del mensaje.

Índices

CREATE INDEX ON notifications (tenant_id, app_id, created_at DESC);   -- consultas por app
CREATE INDEX ON notifications (tenant_id, app_id, target_user_id);       -- filtro personales
CREATE INDEX ON notifications (expires_at);                               -- cleanup
CREATE INDEX ON notifications USING GIN (metadata);                   -- metadata JSONB

El índice GIN permite consultar sobre la columna JSONB sin full scan. Las queries tipo metadata @> '{"teamId": "soporte"}' son eficientes.

Cómo se lee

La query SQL completa que usa el backend para obtener las notificaciones de un usuario:

SELECT n.*, nr.read_at
FROM notifications n
LEFT JOIN notification_reads nr
  ON nr.notification_id = n.id
  AND nr.user_id = 'pedro-uuid'
WHERE n.tenant_id = 'tenant-1'
  AND (n.expires_at IS NULL OR n.expires_at > NOW())
  AND n.deleted_at IS NULL
  AND (
    ── Personales ──
    n.target_user_id = 'pedro-uuid'     ← solo Pedro

    OR (
      ── Broadcasts ──
      n.target_user_id IS NULL
      AND (
        n.metadata IS NULL                ← sin metadata = todos ven
        OR n.metadata->>'teamId' = 'soporte'  ← coincide con equipo
        OR n.metadata->>'teamId' = 'ti'
      )
    )
  )
ORDER BY n.priority DESC, n.created_at DESC
LIMIT 5

Campos del response:

{
  notifications: [{
    id, appId, title, message,
    type: 'info' | 'success' | 'warning' | 'error',
    priority: 'low' | 'normal' | 'high' | 'urgent',
    actionUrl, metadata, createdAt,          // ISO 8601
    isRead, readAt,                          // de notification_reads
    isDeleted, deletedAt                     // soft delete
  }],
  total, skip, take
}

Targeting

1. Broadcast (todos los usuarios del tenant+app)

await api.create({
  appId: 'nexo',
  title: 'Mantenimiento programado',
  // Sin targetUserId ni metadata → visible para TODOS
});

2. Usuario específico (caso raro 1:1)

await api.create({
  appId: 'nexo',
  title: 'Te asignaron el ticket SUP-001',
  targetUserId: 'pedro-uuid',   // solo Pedro lo ve
});

3. Por equipo (metadata app-specific)

// Creación: la app agrega metadata con el ID del equipo
await api.create({
  appId: 'nexo',
  title: 'Ticket SUP-001 asignado',
  metadata: { teamId: 'soporte' },   // ← app-specific
});

// Lectura: el usuario pasa sus equipos al filtro
const result = await api.getNotifications({
  appId: 'nexo',
  metadata: { teamId: ['soporte', 'ti'] },  // OR: soporte O ti
});

4. OR plano multi-key

const result = await api.getNotifications({
  appId: 'nexo',
  metadata: {
    teamId: ['soporte', 'ti'],
    projectId: ['proyecto-alfa'],
  },
  // OR plano entre todos los valores de todas las keys
});
💡 Reglas del filtro combinado
  • Personales (targetUserId = userId) → siempre visibles
  • Broadcasts sin metadata (metadata IS NULL) → visibles para todos los usuarios (legacy)
  • Broadcasts con metadata → visibles solo si al menos un valor del filtro coincide
  • OR plano: todos los valores de todas las keys se combinan en OR
  • Un usuario puede tener N equipos, y el array OR acepta todos

const api = new NotificationsAPI({
  apiUrl: import.meta.env.VITE_CORE_API_URL || '/api',

function NotificationCenter({ user }) {
  const {
    notifications, unreadCount, isLoading,
    markAsRead, markAllAsRead,
  } = useNotifications({
    api,
    appId: 'nexo',
    filter: { metadata: { teamId: user.teams } },  // ← app pasa contexto
    limit: 5,
  });

  if (notifications.length === 0) {
    return <p>Sin notificaciones</p>;
  }

  return (
    <div>
      <button onClick={markAllAsRead}>
        Campana ({unreadCount})
      </button>
      {notifications.map(n => (
        <div key={n.id} onClick={() => markAsRead(n.id)}
             className={!n.read ? 'bg-muted/30' : ''}>
          <strong>{n.title}</strong>
          <p>{n.message}</p>
        </div>
      ))}
    </div>
  );
}

Integración desde backend (BFF)

Cada app necesita un servicio para enviar notificaciones. Ejemplo completo:

// services/notifications.service.ts
import { NotificationsAPI } from '@tgtone/notifications-sdk';

const CORE_API_URL = process.env.CORE_API_URL!;

export function createNotificationsService(req) {
  const token = req.headers.authorization?.replace('Bearer ', '') || null;
  return new NotificationsAPI({
    apiUrl: CORE_API_URL,
    getToken: () => token,
  });
}
// controller.ts — uso
import { createNotificationsService } from '../services/notifications.service';

app.post('/api/tickets', async (req, res) => {
  const ticket = await crearTicket(req.body);

  const notif = createNotificationsService(req);
  await notif.create({
    appId: 'nexo',
    title: `Ticket ${ticket.id} creado`,
    message: `${ticket.numero} fue creado por ${req.user.name}`,
    type: 'info',
    actionUrl: `/tickets/${ticket.id}`,
    metadata: { teamId: ticket.teamId },  // ← targeting por equipo
  });

  res.json(ticket);
});
⚠️ Nota importante

El token JWT debe pertenecer a un usuario del tenant donde se crea la notificación. Para notificaciones de sistema (sin usuario), se requiere una API Key. Contacta al equipo de core backend para habilitar esta opción.

Manejo de errores

Toda llamada puede lanzar NotificationsError:

import { NotificationsError } from '@tgtone/notifications-sdk';

try {
  await api.create({ appId: 'baco', title: '', message: '' });
} catch (err) {
  if (err instanceof NotificationsError) {
    switch (err.statusCode) {
      case 401: /* token inválido */ break;
      case 400: /* validación */ break;
      case 404: /* no encontrado */ break;
    }
  }
}
