Modelo de datos

1 notificación = 1 registro en BD. El sistema es 1:N puro. El filtro se aplica en lectura, no en creación. Sin duplicación del mensaje por destinatario.

1 broadcast = 1 fila en notifications. Cada usuario que la lee = 1 fila en notification_reads. Sin duplicación del mensaje.

Índices

CREATE INDEX ON notifications (tenant_id, app_id, created_at DESC);  -- consultas por app
CREATE INDEX ON notifications (tenant_id, app_id, target_user_id);   -- filtro personales
CREATE INDEX ON notifications (expires_at);                           -- cleanup
CREATE INDEX ON notifications USING GIN (metadata);                  -- metadata JSONB

El índice GIN en la columna JSONB permite consultas eficientes como metadata @> '{"teamId": "soporte"}'. Sin él, cada consulta haría un full scan de la tabla.

Diagramas

Flujo end-to-end

Pedro cierra un ticket. La notificación viaja del backend al frontend de María (equipo soporte) en segundos.

Separación: Core vs App

El core no sabe qué es un equipo o proyecto. Solo almacena y filtra metadata. Cada app define sus propios filtros.

Cómo se lee

La query SQL completa que usa el backend para obtener las notificaciones de un usuario. Combina personales + broadcasts (con o sin metadata):

SELECT n.*, nr.read_at
FROM notifications n
LEFT JOIN notification_reads nr
  ON nr.notification_id = n.id
  AND nr.user_id = 'pedro-uuid'
WHERE n.tenant_id = 'tenant-1'
  AND (n.expires_at IS NULL OR n.expires_at > NOW())
  AND n.deleted_at IS NULL
  AND (
    -- Personales --
    n.target_user_id = 'pedro-uuid'

    OR (
      -- Broadcasts --
      n.target_user_id IS NULL
      AND (
        n.metadata IS NULL                  -- sin metadata = todos ven
        OR n.metadata->>'teamId' = 'soporte' -- coincide con equipo
        OR n.metadata->>'teamId' = 'ti'
      )
    )
  )
ORDER BY n.priority DESC, n.created_at DESC
LIMIT 5

Arquitectura: backend vs frontend

El SDK se usa en ambos lados, pero con responsabilidades distintas.

Backend (BFF) → Crear notificaciones

Las notificaciones que representan eventos de negocio (trasiego completado, stock bajo, ticket asignado) se crean exclusivamente desde el backend de cada app.

MotivoExplicación
Seguridad El backend inyecta tenantId y createdBy desde el JWT ya verificado. Desde el frontend, un usuario con DevTools podría forjar notificaciones falsas.
Atomicidad La notificación se crea si y solo si la operación de negocio se completó. Sin ventana de inconsistencia.
Eventos async Muchas notificaciones (suscripción expiró, stock mínimo) se originan en workers, schedulers o webhooks donde no hay frontend presente.
Trazabilidad createdBy registra al usuario que ejecutó la acción. Si el frontend creara la notif, sería el token del usuario actual, no de quien originó el evento.

El frontend usa el SDK solo para lectura y acciones del usuario sobre sus propias notificaciones:

Targeting

1. Broadcast (todos los usuarios del tenant+app)

await api.create({
  appId: 'nexo',
  title: 'Mantenimiento programado',
  // Sin targetUserId ni metadata → visible para TODOS
});

2. Usuario específico (caso raro 1:1)

await api.create({
  appId: 'nexo',
  title: 'Te asignaron el ticket SUP-001',
  targetUserId: 'pedro-uuid',   // solo Pedro lo ve
});

3. Por equipo (metadata app-specific)

// Creación: la app agrega metadata con el ID del equipo
await api.create({
  appId: 'nexo',
  title: 'Ticket SUP-001 asignado',
  metadata: { teamId: 'soporte' },
});

// Lectura: el usuario pasa sus equipos al filtro
const result = await api.getNotifications({
  appId: 'nexo',
  metadata: { teamId: ['soporte', 'ti'] },  // OR: soporte O ti
});

4. OR plano multi-key

const result = await api.getNotifications({
  appId: 'nexo',
  metadata: {
    teamId: ['soporte', 'ti'],
    projectId: ['proyecto-alfa'],
  },
  // OR plano entre todos los valores de todas las keys
});
💡 Reglas del filtro combinado
  • Personales (targetUserId = userId) → siempre visibles
  • Broadcasts sin metadata (metadata IS NULL) → visibles para todos los usuarios (legacy)
  • Broadcasts con metadata → visibles solo si al menos un valor del filtro coincide
  • OR plano: todos los valores de todas las keys se combinan en OR
  • Un usuario puede tener N equipos, y el array OR acepta todos

import { useState } from 'react';
import { NotificationsAPI } from '@tgtone/notifications-sdk';
import { useNotifications } from '@tgtone/notifications-sdk/react';

const api = new NotificationsAPI({
  apiUrl: import.meta.env.VITE_CORE_API_URL || '/api',
  getToken: () => localStorage.getItem('tgtone_auth_token'),
});

function NotificationCenter({ user }) {
  const { notifications, unreadCount, isLoading, markAsRead, markAllAsRead } = useNotifications({
    api,
    appId: 'nexo',
    filter: { metadata: { teamId: user.teams } },
    limit: 5,
  });

  if (isLoading) return <p>Cargando...</p>;
  if (notifications.length === 0) return <p>Sin notificaciones</p>;

  return (
    <div>
      <button onClick={markAllAsRead}>Campana ({unreadCount})</button>
      {notifications.map(n => (
        <div key={n.id} onClick={() => markAsRead(n.id)}>
          <strong>{n.title}</strong>
          <p>{n.message}</p>
        </div>
      ))}
    </div>
  );
}

Backend (BFF)

// services/notifications.service.ts
import { NotificationsAPI } from '@tgtone/notifications-sdk';

const CORE_API_URL = process.env.CORE_API_URL!;

export function createNotificationsService(req) {
  const token = req.headers.authorization?.replace('Bearer ', '') || null;
  return new NotificationsAPI({ apiUrl: CORE_API_URL, getToken: () => token });
}
// controller.ts
app.post('/api/tickets', async (req, res) => {
  const ticket = await crearTicket(req.body);
  const notif = createNotificationsService(req);

  await notif.create({
    appId: 'nexo',
    title: `Ticket ${ticket.id} creado`,
    type: 'info',
    metadata: { teamId: ticket.teamId },
  });

  res.json(ticket);
});
⚠️ Importante

El token JWT debe pertenecer a un usuario del tenant donde se crea la notificación. Para notificaciones de sistema, contactar al equipo de core para habilitar API Key.

Manejo de errores

Toda llamada lanza NotificationsError:

import { NotificationsError } from '@tgtone/notifications-sdk';

try {
  await api.create({ appId: 'baco', title: 'test', message: 'test' });
} catch (err) {
  if (err instanceof NotificationsError) {
    switch (err.statusCode) {
      case 401: /* token inválido */ break;
      case 400: /* validación */ break;
      case 404: /* no encontrado */ break;
    }
  }
}
Método helperDescripción
err.isUnauthorized()statusCode === 401
err.isNotFound()statusCode === 404
err.isValidationError()statusCode === 400
